# L4 and LPS

*Kind: integration guide · Audience: users · Status: current (2026-09-30)*

L4 is a language for laws and contracts in the form of programs. The Centre for
Computational Law of Singapore Management University (SMU) made L4. Now the company
Legalese develops L4. An L4 contract tells who must do something, who may do
something, and who must not do something. The contract also tells the latest date for
each action, and what occurs after it:

```
`the sale contract` MEANS
    PARTY `the seller`  MUST `deliver the goods`  WITHIN 14
    HENCE
        PARTY `the buyer`  MUST `pay the invoice`  WITHIN 30
        HENCE FULFILLED
        LEST BREACH
    LEST
        PARTY `the seller`  MAY `cancel the order`
```

`MUST` is an obligation, `MAY` is a permission and `SHANT` is a prohibition. `HENCE`
tells what occurs when a party satisfies the obligation. `LEST` tells what occurs
when a party does not satisfy the obligation before its deadline. L4 tests a contract
with a `#TRACE`. A `#TRACE` is a list of events on given days. The result of a trace
is the condition of the contract after those events. The contract is fulfilled, or it
is breached, or some obligations are still open.

**File ▸ Open…** in this editor opens an `.l4` file. The editor opens the contracts of
the file as a program in Logical English for LPS. LPS (Logic Production System) runs
this program in time. The rules of the same file are the part that tells what follows
from what. These rules become an ordinary Logical English program, which the
translator writes adjacent to the LPS program. The documents of the Logical English
editor describe this program
([L4 and Logical English](https://le2.logicalcontracts.com/docs/user/integrations/l4)).
The translator is part of the Logical English installation. Thus the translator needs
LE2, the Logical English editor, adjacent to LPS2 (`LPS_LE2_LIB`, refer to
[Logical English](../guide/ide.md#logical-english)). It also needs the InsurLE
extensions, as on the hosted service. If the translator is not available, an `.l4`
file opens as plain text.

## At a glance

| Direction | Where (menu item) | Files | What you get | Checked against |
|---|---|---|---|---|
| L4 → Logical English for LPS | **File ▸ Open…** | `.l4` | each obligation, permission and prohibition becomes a fluent; each `#TRACE` becomes a scenario with the result of L4 above it; the rules are written adjacent to the program | the evaluator of L4: of the 95 traces in the examples of L4, 87 end with the same result as L4, none are different, and 8 are not translated (refer to below) |

A fluent is a fact that can change with time. A scenario is a set of events and facts
that the program runs. There is no translation in the opposite direction yet: the
editor does not write L4.

## How to use it

### The twins among the examples

A twin is a program that a translator made from the source of a different system.
The twins of the examples of L4 are in `examples/migration/l4/`. They are these:

- the sale contract and the charity contract of the foundation course of L4
- the promissory note (a loan that the borrower pays back in twelve instalments)
- the regulatory course and the contracts course
- the reference examples of `MUST`, `MAY`, `SHANT`, `PARTY` and `BECAUSE`
- a performance award for a chief executive
- New York environmental review.

Each folder keeps its L4 file in `sources/`, with the licence of L4 (Apache 2.0). To
open and run a twin, do these steps:

1. Select **File ▸ Open example from server**.
2. Open the folder *Migration twins*.
3. Select a twin.
4. Run the twin.

The timeline shows the fluent of each obligation. The fluent starts in the cycle
where the obligation starts. The fluent continues to the cycle where a party
satisfies the obligation or misses its deadline.

### Opening your own L4 file

Do these steps:

1. Select **File ▸ Open…**.
2. Select the `.l4` file.

The note at the top of the program gives the counts of the ledger of the translator.
The ledger is the record of what the translator did. The note tells you how many parts
of the file the translator translated exactly. The note also tells you how many parts
have wording that the translator had to make, and how many parts it could not
translate. The parts that the translator could not translate stay in the program as
comments, each with its reason. The translator never removes them. **View ▸ The
original this was converted from** shows the L4 file. When the server has the
evaluator of L4, the comment above each scenario is the result of L4 for that trace.

### Running one trace

A twin has one scenario for each `#TRACE`. The name of each scenario comes from the
line of the trace (`trace_33`). A run uses the first scenario. When there is more than
one scenario, the run tells you this. To run a different scenario from the command
line, give its name:

```sh
LPS_LE2_LIB=<an LE2 checkout> ./lps run examples/migration/l4/sale_contract/sale_contract.le --scenario trace_33
```

## How an L4 contract maps to LPS

| L4 | Logical English for LPS |
|---|---|
| an obligation `PARTY p MUST a WITHIN d` | a fluent that is true while the obligation is open: `the sale contract obliges the seller to deliver the goods by day 14 as its first obligation` |
| `MAY`, `SHANT` | the same, with `permits` and `forbids` |
| the start of the contract (`#TRACE c AT day`) | an event, `the contract the sale contract starts on day 0`. The law of this event starts the first obligations |
| an event of the trace, `PARTY p DOES a AT day` | an event with the day as its last place: `the seller does deliver the goods on day 10`; one event in each cycle, in the sequence of the trace |
| `HENCE` | the law of the event that satisfies the obligation: the law stops the fluent and starts what follows |
| `LEST` | the law of the first event after the deadline: the law stops the fluent and starts what follows (refer to below) |
| `WAIT UNTIL day` | the event `the clock reaches day …`: time passes and nothing occurs |
| `FULFILLED`, `BREACH`, `BREACH BY p BECAUSE r` | the fluents `the contract is fulfilled`, `the contract is breached`, `the contract is breached by *a party* because *a reason*`; a missed deadline and a forbidden action each have their own breach, which names the party and the day |
| `RAND`, `ROR` (obligations that a party must satisfy all of, or any one of) | two parts, and a law that joins them |
| `PROVIDED`, `EXACTLY` (a condition on the action, an exact value) | conditions of the law that satisfies the obligation |
| a contract that calls itself with new values (the instalments of the promissory note) | the values are places of the fluent, and each payment starts the fluent again with the amount that the borrower still owes |

## What L4 does that surprises readers

The twins do the same as the evaluator of L4 (the repository of L4 at commit
`5e082cf`, 29 September 2026). This includes five behaviours that the L4 text does not
make clear:

- **The system sees a missed deadline only when a subsequent event occurs.** Nothing
  occurs on the deadline. The first event after the deadline starts what the `LEST`
  branch tells. That event does not count for the new obligation.
- **Each deadline starts from the time when its obligation started**, not from the
  start of the contract. The promissory note calculates its instalments as days after
  the start of the loan. Thus in the promissory note, the deadlines move later with
  each payment.
- **A payment of the penalty of the promissory note ends all of the note.** The reason
  is that the `HENCE` of the penalty obligation is `FULFILLED`.
- **A name in an action gives a value to the name. It does not compare.** In
  `MUST pay amount`, `amount` is an input of the contract. But any payment satisfies
  the obligation. Only `EXACTLY` compares the action with the input.
- **A permission that a party does not use still has a result.** Possibly
  `PARTY p MAY act WITHIN d HENCE next` passes its deadline, and the party did not use
  the permission. Then the evaluator of L4 starts `next` at the next event, as if the
  party used the permission. But the documentation of L4 tells that a permission that
  a party does not use ends the contract as fulfilled. The twins do the same as the
  evaluator, which gives the answers of L4.

## What is not translated

The Logical English guide gives a list of all the things that the translator does
not support yet, for rules and for contracts
([L4 and Logical English](https://le2.logicalcontracts.com/docs/user/integrations/l4#what-is-not-supported-yet)).
For contracts:

The translator does not translate eight traces of the examples of L4. Each of these
traces stays as a pending scenario with its reason. Seven of these traces are in the
performance award for a chief executive. Their reasons are these:

- a list that `FOLLOWED BY` separates into parts
- a record field of a value that is known only while the contract runs
- a function with an incorrect number of inputs.

One trace is in New York environmental review. Its reason is a function with an
incorrect number of inputs. The translator translates `RAND` and `ROR`, but not one
inside the other. The editor does not write L4 back.
