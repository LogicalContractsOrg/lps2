# L4 and LPS

*Kind: integration guide · Audience: users · Status: current (2026-09-29)*

L4 is a language for writing laws and contracts as programs. The Centre for
Computational Law of Singapore Management University (SMU) built it, and the
company Legalese develops it now. An L4 contract says who must, may or must
not do something, by when, and what follows:

```
`the sale contract` MEANS
    PARTY `the seller`  MUST `deliver the goods`  WITHIN 14
    HENCE
        PARTY `the buyer`  MUST `pay the invoice`  WITHIN 30
        HENCE FULFILLED
        LEST BREACH
    LEST
        PARTY `the seller`  MAY `cancel the order`
```

`MUST` is an obligation, `MAY` a permission and `SHANT` a prohibition.
`HENCE` says what follows when the obligation is met, and `LEST` what follows
when its deadline is missed. L4 tests a contract with a `#TRACE`, a list of
events on given days. The result of a trace is how the contract stands after
those events: fulfilled, breached, or what is still open.

**File ▸ Open…** in this editor takes an `.l4` file and opens its contracts
as a program in Logical English for LPS, which LPS (Logic Production System)
runs in time. The rules of the same file, the part that says what follows
from what, become an ordinary Logical English program, written beside it and
documented in the Logical English editor
([L4 and Logical English](https://le2.logicalcontracts.com/docs/user/integrations/l4)).
The translator belongs to the Logical English installation, so it needs
LE2, the Logical English editor, beside LPS2 (`LPS_LE2_LIB`, see
[Logical English](../guide/ide.md#logical-english)), with the InsurLE
extensions, as on the hosted service. Without it, an `.l4` file opens as
plain text.

## At a glance

| Direction | Where (menu item) | Files | What you get | Checked against |
|---|---|---|---|---|
| L4 → Logical English for LPS | **File ▸ Open…** | `.l4` | each obligation, permission and prohibition a fluent, each `#TRACE` a scenario with L4's result above it, the rules written beside it | L4's own evaluator: of the 95 traces in L4's examples, 87 end where L4's do, none differ, and 8 are not translated (below) |

There is no way back yet: the editor does not write L4.

## How to use it

### The twins among the examples

The twins of L4's examples are in `examples/migration/l4/`: the sale
contract and the charity contract of L4's foundation course, the promissory
note (a loan repaid in twelve instalments), the regulatory and contracts
courses, the reference examples of `MUST`, `MAY`, `SHANT`, `PARTY` and
`BECAUSE`, a chief executive's performance award, and New York environmental
review. Each folder keeps its L4 file under `sources/`, with L4's licence
(Apache 2.0). Open a twin with **File ▸ Open example from server**, in the
folder *Migration twins*, and run it. The timeline shows each obligation's
fluent from the cycle it starts to the cycle it is met or missed.

### Opening your own L4 file

Choose **File ▸ Open…** and pick the `.l4` file. The note at the top of the
program gives the counts of the translator's ledger: how many parts of the
file were translated exactly, how many with a wording the translator had to
invent, and how many could not be translated. What could not be translated
stays in the program as a comment with its reason, never dropped. **View ▸
The original this was converted from** shows the L4 file. When L4's own
evaluator is installed on the server, the comment above each scenario is L4's
result for that trace.

### Running one trace

A twin has one scenario per `#TRACE`, named after the trace's line
(`trace_33`). A run uses the first scenario, and says so when there are
several. To run another one from the command line, name it:

```sh
LPS_LE2_LIB=<an LE2 checkout> ./lps run examples/migration/l4/sale_contract/sale_contract.le --scenario trace_33
```

## How an L4 contract maps to LPS

| L4 | Logical English for LPS |
|---|---|
| an obligation `PARTY p MUST a WITHIN d` | a fluent that holds while the obligation is open: `the sale contract obliges the seller to deliver the goods by day 14 as its first obligation` |
| `MAY`, `SHANT` | the same, with `permits` and `forbids` |
| the start of the contract (`#TRACE c AT day`) | an event, `the contract the sale contract starts on day 0`, whose law starts the first obligations |
| an event of the trace, `PARTY p DOES a AT day` | an event with the day as its last place: `the seller does deliver the goods on day 10`; one event per cycle, in the trace's order |
| `HENCE` | the law of the event that meets the obligation: it ends the fluent and starts what follows |
| `LEST` | the law of the next event after the deadline: it ends the fluent and starts what follows (see below) |
| `WAIT UNTIL day` | the event `the clock reaches day …`: time passes and nothing is done |
| `FULFILLED`, `BREACH`, `BREACH BY p BECAUSE r` | the fluents `the contract is fulfilled`, `the contract is breached`, `the contract is breached by *a party* because *a reason*`; a missed deadline and a forbidden action each have a breach of their own, naming the party and the day |
| `RAND`, `ROR` (obligations that must all, or any one, be met) | two parts, and a law that joins them |
| `PROVIDED`, `EXACTLY` (a condition on the action, an exact value) | conditions of the law that meets the obligation |
| a contract that calls itself with new values (the promissory note's instalments) | the values are places of the fluent, and each payment starts the fluent again with the amount still owed |

## What L4 does that surprises readers

The twins reproduce L4's own evaluator, including four behaviours that the
L4 text does not make obvious:

- **A missed deadline is noticed only when something next happens.** Nothing
  happens on the deadline itself. The next event after it starts what the
  `LEST` branch says, and that event does not count towards the new
  obligation.
- **Each deadline counts from the moment its obligation started**, not from
  the start of the contract. In the promissory note, whose instalments are
  computed as days after the start of the loan, the deadlines drift further
  with each payment.
- **Paying the promissory note's penalty ends the whole note**, because the
  penalty obligation's `HENCE` is `FULFILLED`.
- **A name inside an action binds rather than compares.** In `MUST pay
  amount`, where `amount` is an input of the contract, any payment meets the
  obligation. Only `EXACTLY` compares the action with the input.

## What is not translated

Eight traces of L4's examples are not translated, and each stays as a pending
scenario with its reason: seven of the chief executive's performance award
(a list taken apart with `FOLLOWED BY`, a record field of a value known only
while the contract runs, and a function applied to the wrong number of
inputs) and one of New York environmental review (a function applied to the
wrong number of inputs).
