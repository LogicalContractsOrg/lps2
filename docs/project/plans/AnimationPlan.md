# Better animations: what a picture of a program should show

*Kind: design note · Status: part built (§4 is in), the rest proposed · 2026-09-20*

Where "Animate in 2D/3D" stands, why the pictures it makes are thin, and four
proposals for making them say something. §4 is built and shipped with this note;
§§5–7 are the proposals, smallest first.

The prompt is a user's, after watching the assistant animate
`examples/collections/kowalski-book/underground.lps` twice:

> The 2D and 3D animations generated by the assistant seem still very basic and
> erratic. Might our Automaton states provide hints about relevance or focus?
> Might an Interactive Fiction perspective help — a 2D/3D rendering of an
> execution tells its "narrative" graphically. Can one detect high level
> patterns, either in the source (composite events, intensional fluents and
> their dependencies) or in the execution trace, that guide the narrative
> building hence the scene construction? Perhaps use multiple scenes for
> important program states.

---

## 1. Where it stands

Scene generation is already split in two (§I.10.4e, `src/edges/lps_scene.pl`):
the model produces a **plan** — which containers exist, which things live in
them, which fluent template puts a thing where — and this repository computes
the geometry. The model never writes a coordinate. That split fixed the first
generation of failures (three animals at one point, a label off the canvas) and
it is not in question here: everything below keeps it and pushes more of the
*judgement* to the side that can compute.

What the split does not do is decide **what the picture is about**. That was
left to the model reading the source, and the model reads the source the way a
reader does: it draws the nouns that appear in the sentence it was asked about.

## 2. The two failures, diagnosed

Both come from the same run of the Underground notice — five fluents:
`emergency/1`, `penalty/1`, `alerted/0`, `in_station/0`, `stopped/0`.

**Failure A — two of five.** The plan drew `emergency` and `penalty` as gauges
and left `alerted`, `in_station` and `stopped` out. This was not the model being
lazy: those three are *propositional* fluents, and the plan grammar had **no
shape for a fluent that is simply true or false**. A gauge needs a `value_var`;
a layer needs a place and a thing; a stack needs a support. A flag fits none of
them, so a program whose state is flags — which is most of the book's chapter-1
programs, and every contract-shaped program — could not be drawn at all. The
model chose the two fluents it *could* express and said nothing about the rest.

**Failure B — `_24584:fire`.** The generated clause read

```prolog
display(emergency(Value), [ …, label:(Emergency:Value) ]).
```

`Emergency` is the label the model chose, written into a Prolog term
**unquoted**: capitalised, so a variable, so it printed as `_24584`. Two more
things were wrong in the same picture: the gauge captions sat four units above
their boxes and text is drawn *downward* from its point, so each caption landed
across the top of the box it named; and the title sat where a caption would be.

None of these is a model failure. They are all failures of the part that was
supposed to be mechanical.

## 3. The principle

> **A picture of a program is a picture of what changes in it.** Which fluents
> change is a property of the *run*, not of the source, so it is not something
> to ask a language model to infer — the engine knows it exactly.

This is the same move as taking coordinates away: compute what can be computed,
and give the model the result rather than the question. It is also what the
neuro-symbolic interactive-fiction work converged on independently — the
symbolic state is *rendered for* the narrative layer, and what the narrative
layer produces is *validated against* the state before it is used
([IVIE](https://arxiv.org/html/2606.13348v1),
[world-state transformations](https://pith.science/paper/2605.24719)).

## 4. Built with this note

1. **Lamps.** A gauge with no `value_var` is a lamp: the box is there while the
   fluent holds and gone while it does not, under a caption that stays. This is
   the fourth plan shape, and it is what Failure A was missing
   (`lps_scene.pl`, `read_gauge/3`, `render_gauge/1`).
2. **The run is analysed before the model plans.** `moving_material/3`
   (`lps_assistant.pl`) compiles the buffer, runs it, reads the timeline and
   puts in the prompt a section **WHAT CHANGES**: every fluent whose instances
   come and go, with an example, and separately those that never change ("these
   are backdrop at most"). The rule beside it says the plan must cover them.
3. **A plan that leaves one out is handed back.** `layout_gaps/4` compares the
   plan's templates against that same list after the clauses are written; a
   plan that misses a moving fluent is *not* the end of the turn — the model is
   told which, and may plan again or finish and say why one is not worth
   drawing.
4. **Labels are quoted, and captions clear their boxes.** Failure B, both
   halves, with a regression test for each (`tools/m8a_test.pl`).
5. **The generated clauses are read back.** `free_variable_diags/2` reports any
   lone variable in what was written — the general form of Failure B, since
   every variable this generator means to write is used at least twice.

That is the floor: every animation now shows everything that moves, or says why
not. The rest of this note is about making it *good*.

## 5. Proposal: the automaton says what is worth showing

`lps_automaton/4` (`src/core/lps_explain.pl`) already computes the thing the
user is reaching for. It gives `node(Cycles, Fluents, Cycles, Initial)` — one
node per DISTINCT state, carrying every cycle it was visited at — and
`edge(From, To, Label, Kind)` with `Kind ∈ {event, action}`. Three facts fall
out of it that a scene planner wants and nothing else in the system offers:

- **Which fluents discriminate.** A fluent that has the same truth value in
  every node contributes nothing to the diagram and nothing to the picture: it
  is backdrop, by construction rather than by guess. A fluent that separates two
  nodes is the plot. This is a sharper version of §4's "what moves", and it is
  free — it is a set difference over the nodes.
- **Where the picture should stop.** The automaton's nodes are the distinct
  states; the *cycles* are the frames. A run of 40 cycles through 6 states does
  not want 40 frames, it wants 6, at the cycles where the state changes. The
  timeline scrubber can mark them; a generated animation can key on them.
- **What repeats.** A node visited at several cycles is a loop — the story comes
  back here — and a self-transition (`non_reflexive` drops these) is a beat
  where nothing happened. Both are things a reader wants marked and neither is
  visible in the current picture.

Proposed: `lps_scene_focus/3`, in the core beside the automaton, answering
*discriminating(Fluents), keyframes(Cycles), loops(Nodes)* for a run. It feeds
(a) the prompt, sharpening WHAT CHANGES into WHAT DISTINGUISHES, (b) the 2D/3D
panes, which can offer "next change" rather than "next cycle", and (c) §7.

Cost: small — the automaton is computed already, and this is a projection of it.

## 6. Proposal: read the shapes out of the source, not only the run

The user's second question. The source has structure the run does not show, and
three kinds of it map onto pictures:

- **Composite events** (`e from T1 to T2` built from sub-events) are *acts* in
  the dramatic sense: a span with a beginning and an end, which is what a
  timeline lane or a progress bar is. Drawing a composite as one bar over its
  sub-events is the single most narrative thing the corpus can express, and the
  plan grammar has no word for it today.
- **Intensional fluents** (defined by rules over other fluents) are *derived*:
  they should be drawn differently from stored ones — an outline rather than a
  fill — because they cannot be changed directly and a reader who does not know
  that will look for the event that set them. `p_defaults/2` and the intensional
  declarations are already in the program record.
- **The dependency graph** between them says what to put next to what. Two
  fluents that appear in one rule belong in one region of the picture; a fluent
  nothing depends on belongs at the edge. This is ordinary graph layout applied
  to a graph we already have, and it replaces the current left-to-right order,
  which is the order the model happened to list things in.

Proposed: extend the plan grammar with `spans` (composite events) and mark
intensional fluents automatically — the model should not be *asked* which are
intensional, since the program says so.

## 7. Proposal: several scenes, and the narrative between them

The user's "multiple scenes for important program states", which the literature
would call keyframing a trace
([ReTrace](https://arxiv.org/html/2511.11187v1) does the same for reasoning
traces: a structural view beside a chronological one).

Today a scene is one canvas redrawn per cycle. Proposed instead:

- **A strip.** §5's keyframes, drawn small, side by side, with the transition
  label between them — the automaton's edges, which name the event or action
  that moved the story on. This is a *diagram of the run*, not an animation of
  it, and it is what a reader wants when asking "what happened?" rather than
  "what is true now?".
- **A caption per frame**, written by the model from the transition and the
  state change — one sentence, the narrative layer, grounded in the symbolic
  state the way the IF work grounds it. `lps_session_changes/3` already gives
  initiated/terminated/updated per cycle, which is exactly the material.
- **Zoom.** Clicking a frame opens the full scene at that cycle. The strip is
  the map; the canvas is the place.

This is the largest of the three and the one that changes the IDE, not only the
generator; it should follow §5, which it depends on.

## 8. What not to do

- **Do not ask the model for more geometry.** Everything above moves work the
  other way.
- **Do not let a picture be published that has a free variable in it.** §4.5 is
  the guard; keep it, and keep it a *warning* rather than a refusal — a picture
  with one wrong caption is still a picture, and the note says which.
- **Do not animate what did not change.** A fluent that holds throughout is a
  caption, not a frame.
